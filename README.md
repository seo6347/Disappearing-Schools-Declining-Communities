# 학교가 사라진 다음
### Disappearing Schools, Declining Communities

**학교 세 곳을 하나로 합치면, 아이들의 등굣길과 마을의 교육 기반은 어떻게 달라질까요?**

학교 통폐합은 학교 수의 변화이면서, 학생들이 매일 이동해야 하는 거리와 시간의 변화이기도 합니다. 어떤 지역에서는 여러 학교 가운데 하나가 없어지지만, 다른 지역에서는 마을의 마지막 공립초등학교가 사라질 수 있습니다.

이 프로젝트는 교육부가 발표한 '소규모 학교 혁신을 통한 지역 교육력 제고 방안'(2026.06) 속 통폐합 모델을 근거로 전국 소규모 공립초등학교를 대상으로 **세 학교를 한 학교로 통합하는 반사실적 시나리오**를 구성했습니다. 통합학교의 수용력과 도로 접근성을 고려한 뒤, 학생들의 통학부담이 얼마나 달라지고 어느 읍·면에서 마지막 공립초등학교가 사라지는지 살펴봤습니다.

SBS 데이터사이언스&저널리즘 아카데미 5기 최종 프로젝트에서 출발했으며, 공간자료 처리, 학교 통합 후보 구성, 정수최적화를 이용한 비중복 학교 묶음 선정, 학생 가중 통학부담 분석을 연결했습니다.

## 1. 무엇을 알아보려 했나요?

분석은 다음 세 가지 질문에서 출발했습니다.

1. **어떤 학교들을 통합 가능한 후보로 묶을 수 있을까?**  
   가까이 있다는 이유만으로 학교를 합칠 수는 없습니다. 같은 교육지원청에 속하는지, 통합 후 학생들을 수용할 교실이 있는지, 도로로 이동할 수 있는지도 함께 살펴봤습니다.

2. **학생들이 실제로 이동해야 하는 통학시간은 얼마나 달라질까?**  
   학교와 학교 사이의 거리만으로는 학생들의 부담을 알기 어렵습니다. 학생들이 거주한다고 추정한 지점에서 현재 학교와 통합학교까지의 경로를 각각 계산했습니다.

3. **학교 통합이 지역의 교육 기반에 어떤 공백을 만들까?**  
   학교가 줄어드는 지역 가운데, 특히 마지막 공립초등학교 본교가 사라지는 읍·면을 구분했습니다.

이 분석은 실제 통폐합 예정지를 예측하거나 특정 학교의 폐교를 제안하기 위한 것이 아닙니다. **명시한 조건으로 통폐합을 가정했을 때 나타나는 변화를 살펴보는 시뮬레이션**입니다.

## 2. 주요 결과

아래는 **교실당 학생 수를 28명으로 가정하고, 선정된 각 학교 묶음에서 전체 학생의 평균 통학시간 변화가 가장 작은 통합학교를 선택했을 때**의 결과입니다.

| 살펴본 항목 | 시뮬레이션 결과 |
| --- | ---: |
| 선정된 3개교 통합 묶음 | 720개 |

| 학교를 옮기고 편도 통학시간도 증가하는 학생 규모 | 약 78,462명 |

**학생 규모는 개별 학생을 직접 추적한 인원수가 아니라, 인구 자료를 학교별 실제 재학생 수에 맞춰 보정한 추정치입니다.** 표에서는 이해를 돕기 위해 반올림했습니다. 통학시간 관련 수치는 경로 분석이 가능한 학생을 기준으로 계산했습니다.

평균 증가 시간 6.0분은 전체 학생의 평균이 아니라, **학교를 옮기면서 통학시간이 증가한 학생들만의 평균**입니다. 시간이 줄어든 학생이나 같은 학교에 계속 다니는 학생까지 포함하면 다른 값이 됩니다.
e.g. 학교를 옮긴 학생들을 대상으로 하면 평균 4.4분이 증가합니다. (학교를 옮기면서 통학시간이 감소한 경우도 존재합니다.) 

또한 ‘440곳’은 이 시나리오에서 마지막 **공립초등학교 본교**가 사라지는 읍·면의 수입니다. 해당 지역의 모든 교육시설이 없어지거나 지역소멸이 발생한다는 뜻은 아닙니다.

## 3. 어떤 자료를 사용했나요?

학교의 위치와 학생 수, 통학구역, 집계구별 인구, 도로 이동경로를 연결했습니다.

| 자료 | 분석에 사용한 정보 | 제공 파일 |
| --- | --- | --- |
| 학교 정보 | 학교 위치, 실제 재학생 수, 일반교실 수, 교육지원청, 작은학교 분류 등 | `elementary_master.csv` |
| 학교와 통학구역의 연결 정보 | 각 통학구역에 연결된 학교 | `school_area_master.csv` |
| 통학구역 지도 | 학생 거주 추정 지점을 학교에 연결하기 위한 경계 | `elementary_polygon.gpkg` |
| 집계구별 인구와 위치 | 연령별 인구, 대표점, 행정구역 연결에 필요한 경계 | `census_demand_points.csv`, `census_demand_points.gpkg` |
| 학교 간 도로경로 | 통합 후보 학교 사이의 이동시간과 거리 | `api_routes/school_road_routes.csv` |
| 집계구 대표점과 학교 간 도로경로 | 통합 전후 학생 통학부담 계산 | `team_route_results/`의 경로 파일 |

**집계구**는 인구통계를 작성하기 위해 나눈 작은 공간 단위입니다. 분석에서는 집계구마다 대표 위치 하나를 사용했습니다. 이 위치는 개별 학생의 집 주소가 아닙니다.

지도와 경계가 들어 있는 `.gpkg` 파일은 공간자료를 저장하는 형식입니다. 파일을 직접 열어 수정하지 않아도 분석 코드가 읽어 사용합니다.

공개 데이터에는 학교·통학구역 연결과 공간자료 정리 등 사전 작업이 반영되어 있습니다. 현재 저장소는 **이렇게 준비된 입력 자료부터 최종 분석 결과를 만드는 과정**을 다룹니다.

## 4. 어떻게 분석했나요?

### ① 학생들이 어디에서 학교에 다니는지 추정했습니다

집계구의 5-9세 인구와 10-14세 인구에 각각 3/5를 적용해 초등학령인구를 추정했습니다. 각 집계구의 대표점이 어느 통학구역에 속하는지 확인하고, 연결된 공립초등학교에 인구를 배분했습니다.

이 추정값의 합계가 학교별 실제 재학생 수와 맞도록 보정했습니다. 따라서 계산에 쓰이는 학생 수에는 소수가 포함될 수 있습니다. 예를 들어 ‘학생 가중치 2.5’는 특정 학생의 절반을 뜻하는 것이 아니라, 그 지점에 배분된 분석상 학생 규모를 의미합니다.

통학구역에 연결되지 않는 지점이나 보정이 어려운 학교는 별도로 구분합니다.

관련 코드: [학생분포 추정](scripts/01_estimate_current_student_distribution.py) · [통학구역 미배정 지점 분석](scripts/01-1_analyze_no_zone_sensitivity.py)

### ② 가까운 세 학교를 통합 후보로 묶었습니다

학교 마스터에서 작은학교로 분류된 공립초등학교 본교 가운데, 학생분포 보정과 위치 정보 등의 조건을 충족한 학교를 후보로 삼았습니다.

같은 교육지원청에 속하고 학교 간 직선거리가 10km 이하인 두 학교를 연결한 뒤, 이 연결을 통해 하나로 이어지는 세 학교의 조합을 만들었습니다.

여기서 10km는 후보를 찾는 기준입니다. 실제 도로거리나 통학시간을 의미하지 않으며, 연결된 세 학교의 모든 쌍이 반드시 10km 이내라는 뜻도 아닙니다.

관련 코드: [거리 기준 비교](scripts/02-1_analyze_distance_graph_sensitivity.py) · [학교 연결과 3개교 후보 생성](scripts/02-2_build_adjacency_graph_and_triples.py)

### ③ 수용력과 도로 접근성을 확인했습니다

각 후보에 속한 세 학교를 한 번씩 통합학교로 가정했습니다.

통합학교가 세 학교의 학생을 모두 수용할 수 있는지 판단하기 위해 **통합학교의 일반교실 수 × 교실당 학생 수**를 계산했습니다. 초기에는 교실당 28명과 19명을 비교했으며, 이후 통학부담과 학교 공백 분석은 **28명 기준인 CAP28**로 진행합니다.

도로 접근성도 함께 확인했습니다. 페리가 필요한 통합안은 제외하고, 학교 간 이동시간이 80분을 초과하거나, 40분을 초과하면서 도로거리가 직선거리의 3배를 넘는 통합안도 제외했습니다.

적격 후보가 정해진 뒤에는 한 학교가 여러 통합 묶음에 중복되지 않도록 조합을 선택했습니다. 먼저 묶음 수를 최대화하고, 같은 수의 묶음을 선택할 수 있다면 학교 간 접근시간이 짧은 조합을 우선했습니다.

관련 코드: [수용력 비교](scripts/03-1_evaluate_capacity_scenarios.py) · [도로 접근성 기준 적용](scripts/03-4_finalize_road_access_options.py) · [학교가 중복되지 않는 묶음 선정](scripts/03-5_select_nonoverlapping_clusters.py)

### ④ 학생들의 통합 전후 통학부담을 계산했습니다

선정된 학교에 배정된 집계구 대표점에서 다음 두 경로를 연결했습니다.

- **통합 전:** 대표점에서 현재 학교까지
- **통합 후:** 같은 대표점에서 통합학교까지

두 경로의 시간과 거리 차이를 계산하고, 해당 지점의 학생 가중치를 반영해 집계했습니다. 통학시간이 줄어드는 경우도 결과에 그대로 남깁니다.

각 학교 묶음에서는 가능한 통합학교들 가운데 평균 통학시간 변화가 가장 작은 안과 가장 큰 안을 각각 선택했습니다. 이를 코드에서는 ‘하한안’과 ‘상한안’으로 부릅니다.

이 하한·상한은 **고정된 학교 묶음 안에서 가능한 통합학교들을 비교한 범위**입니다. 전국의 모든 통폐합 방식 가운데 절대적인 최솟값과 최댓값을 구한 것은 아닙니다.

관련 코드: [통학시간 변화 계산](scripts/04-4_calculate_commute_time_changes.py) · [하한·상한 선택](scripts/04-5_select_commute_bounds.py)

### ⑤ 학교 공백과 지역별 차이를 살펴봤습니다

읍·면별로 현재 남아 있는 공립초등학교 본교 수와 시나리오 적용 후 학교 수를 비교했습니다. 이를 통해 마지막 학교가 사라지는 읍·면과 그 지역에 배분된 학생 규모를 계산했습니다.

학교를 옮기고 통학시간이 증가한 학생들에 대해서는 증가 시간의 분포, 교육지원청별 부담, 인구감소지역 분류에 따른 차이를 추가로 살펴봤습니다.

지역별 비교에서 사용하는 교육지원청은 **학생의 현재 배정학교가 소속된 교육지원청**입니다. 학생 거주지 기준의 지역 순위로 해석해서는 안 됩니다.

관련 코드: [학교 공백 분석](scripts/05_analyze_school_voids.py) · [통학부담 분포](scripts/06_analyze_commute_increase_distributions.py) · [지역별 비교](scripts/07_analyze_regional_commute_burden.py)

## 5. 결과를 읽을 때 주의할 점

### 실제 통학버스 운행시간을 계산한 것은 아닙니다

도로경로는 대표점에서 학교까지 곧바로 이동하는 자동차 경로입니다. 여러 학생을 태우기 위한 우회, 승하차, 대기시간은 포함하지 않습니다.

사용한 경로에는 당시 일요일 새벽의 교통상황이 반영되어 있습니다. 실제 평일 등교시간이나 통학버스 운행시간과 같다고 볼 수 없습니다.

### 실제 통폐합 결정에 필요한 모든 조건을 담지는 못했습니다

교실 수와 접근성 외에도 교육과정, 시설 상태, 통폐합 대상 학교들의 교감 등 이해관계, 주민과 학생의 의견, 지역의 생활 여건 등 다양한 조건이 실제 결정에 영향을 줄 수 있습니다. 이 시뮬레이션의 적격 판정은 분석에서 설정한 조건을 통과했다는 의미입니다.

### 학교 소멸과 지역소멸의 인과관계를 입증한 결과는 아닙니다

이 분석이 보여주는 것은 가정한 통폐합 이후의 통학부담과 학교 배치 변화입니다. 이후 인구 유출이나 지역소멸이 실제로 발생하는지는 별도의 자료와 취재가 필요한 질문입니다.

## 6. 직접 같은 분석을 실행하려면

실제 분석에서는 API 호출 등이 사용되었으나, 재현성을 위하여 미리 준비된 데이터를 사용하므로 **API 키 발급이나 별도의 경로 수집은 필요하지 않습니다.**

### 준비물

- Python 3.12
- 내려받은 저장소 코드
- 아래 링크의 `data.zip`
- 명령어를 입력할 터미널. VS Code를 사용해도 됩니다.

### 1) 코드와 데이터 내려받기

이 저장소 상단의 **Code → Download ZIP**을 눌러 코드를 내려받고 압축을 해제합니다.

이어서 [분석 데이터 `data.zip`](https://drive.google.com/file/d/1HgFXBW5J9d3-zDmiuqZ7gLOriOFdx4Df/view?usp=sharing)을 내려받습니다. 데이터 압축은 **`run_pipeline.py`가 있는 폴더에** 해제합니다.

| 항목 | 올바른 위치 |
| --- | --- |
| 전체 실행 파일 | `run_pipeline.py` |
| 패키지 목록 | `requirements.txt` |
| 분석 코드 폴더 | `scripts/` |
| 학교 정보 파일 | `data/01_raw/elementary_master.csv` |
| 공간자료 | `data/01_raw/` 안의 GPKG 2개 |
| 학교 간 경로 | `data/01_raw/api_routes/school_road_routes.csv` |
| 학생 통학경로 | `data/01_raw/team_route_results/` 안의 배치별 CSV |

### 2) VS Code에서 프로젝트 열기

VS Code의 **파일 → 폴더 열기**에서 `run_pipeline.py`가 있는 폴더를 선택합니다.

이후 **터미널 → 새 터미널**을 선택합니다. 아래 명령은 모두 이 프로젝트 폴더에서 실행합니다.

### 3) 실행 환경 준비하기 — Windows

PowerShell 터미널에서 아래 명령을 한 줄씩 실행합니다.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

첫 번째 명령은 이 프로젝트에서 사용할 Python 환경을 만듭니다. 두 번째 명령은 분석에 필요한 패키지를 설치합니다.

### 4) 전체 분석 실행하기 — Windows

패키지 설치가 끝나면 다음 명령을 실행합니다.

```powershell
.\.venv\Scripts\python.exe run_pipeline.py
```

분석은 다섯 단계로 진행됩니다. 마지막에 `[DONE]`이 표시되면 요청한 단계가 완료된 것입니다.

각 실행 단계의 상세 기록은 `logs/`에 저장됩니다. 화면에 새로운 메시지가 바로 나타나지 않더라도 해당 작업의 로그에 진행 내용이 기록될 수 있습니다.

<details>
<summary>macOS·Linux 실행 방법</summary>

Python 3.12가 설치된 상태에서 프로젝트 폴더의 터미널에 입력합니다.

```bash
python3.12 -m venv .venv
./.venv/bin/python -m pip install -r requirements.txt
./.venv/bin/python run_pipeline.py
```

</details>

### 다시 실행하거나 일부 단계만 실행하기

이미 생성한 최종 결과를 덮어쓰며 다시 실행하려면 다음 명령을 사용합니다.

```powershell
.\.venv\Scripts\python.exe run_pipeline.py --overwrite
```

일부 단계만 실행할 수도 있습니다. 예를 들어 앞선 단계의 결과가 있는 상태에서 마지막 분석 단계만 다시 실행하려면 다음과 같이 입력합니다.

```powershell
.\.venv\Scripts\python.exe run_pipeline.py --stage 5 --overwrite
```

| 실행 단계 | 수행하는 작업 |
| --- | --- |
| 1 | 학생분포 추정과 통학구역 미배정 지점 분석 |
| 2 | 거리 기준 비교와 3개교 후보 생성 |
| 3 | 수용력·도로 접근성 평가와 통합 묶음 선정 |
| 4 | 통합 전후 통학부담 계산과 하한·상한 선택 |
| 5 | 학교 공백, 통학부담 분포, 지역별 비교 |

개별 단계는 앞 단계에서 생성한 파일을 사용합니다. 처음 실행할 때는 전체 실행 명령을 사용하는 것이 좋습니다.

## 8. API 수집 코드와 공개 범위

기본 실행은 **당시 수집을 완료한 도로경로 파일을 읽어 계산**합니다. 실시간 교통을 반영하는 경로를 새로 조회하면 같은 출발지와 도착지라도 시간이 달라질 수 있기 때문입니다.

수집 방법을 확인할 수 있도록 API 관련 코드는 남겨두었습니다.

- `03-2_fetch_school_road_routes.py`: 기본 실행에서는 저장된 학교 간 경로를 연결합니다. 실제 API 호출은 별도로 `--execute`를 지정했을 때만 수행합니다.
- `04-2_collect_naver_commute_routes_colab.ipynb`: 팀별 경로 수집에 사용한 선택 도구입니다. 기본 분석에서는 실행하지 않으며, 수집 실행도 기본적으로 비활성화되어 있습니다.

`.env.example`은 API 재수집이 필요한 경우 참고할 수 있는 환경변수 예시입니다. **일반적인 분석 실행에는 `.env`를 만들거나 실제 API 키를 입력할 필요가 없습니다.**

이 저장소는 분석 계산과 결과 생성에 필요한 코드를 중심으로 구성했습니다. 기사 화면, 발표자료, 웹페이지를 제작하기 위한 별도 편집 코드는 포함하지 않습니다.

공개된 입력 자료와 API에서 얻은 정보에는 원자료별 이용 조건이 적용될 수 있습니다. 이 저장소의 공개 자체가 제3자 자료에 대한 별도 이용 허락을 의미하지는 않습니다.
